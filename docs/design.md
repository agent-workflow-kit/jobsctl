# jobsctl: design

Status: designed (interface 0.1.0-design), 2026-10-31. The interface, including every normative rule, is in [interface.md](interface.md); this document records the decisions, the internal architecture and the live verification behind them, and links to the interface instead of restating its rules.

## Role and layer

Generic job queue with concurrency caps, ordering and held jobs. Layer 1 (primitive), fully standalone (architecture §2, C2). jobsctl does not interpret what jobs do and knows nothing about its callers. Its awkit consumers are review-watch and review-respond (optional), ticket-work, and the harness; agent-spawn reads `JOBSCTL_JOB_ID` and forwards cancellation (architecture §9.2).

## Constraints (from architecture §20)

- Jobs run detached under a per-job shim that records exit status and output tail: [Shim](interface.md#shim).
- `jobsctl run` only starts jobs up to the caps and reaps finished shims; it runs as a cron pass or as a loop: [Pass](interface.md#pass). Shims run in their own sessions but are the spawning process's children until they exit: long-lived jobsctl processes (`run --loop`, a waiting `cancel`) reap the children they spawned, by PID, each iteration ([Reaping](interface.md#internal-processes), D48), and a one-shot pass's shims are reparented when it exits. "Reaping finished shims" in the architecture's sense is the pass's reconcile step: [Reconcile](interface.md#reconcile).
- Output tails are masked per `mask_env` (and more, D18); masking is best-effort: [Masking and sanitizing](interface.md#masking-and-sanitizing), [Residual risks](interface.md#residual-risks).

## Decisions

D1–D25 come from the design session; D26–D37 and the revisions marked "(pass 1)" come from review pass 1; D38–D45 and the revisions marked "(pass 2)" come from review pass 2; D46–D47 and the revisions marked "(pass 3)" come from review pass 3; D48 and the revisions marked "(spot checks)" come from the safety and consistency spot checks after pass 3.

| # | Decision | Rationale |

| D1 | Queues are implicit: created on first `add` with `default_cap` (1); `queues.<name>` config sets them; queue `default` when `--queue` is omitted; optional `strict_queues` ([Queues](interface.md#queues)). | jobsctl must not know its callers' queue names (no upward awareness), yet every workflow tool must work out of the box. `queue_created` in the output and the log catches typos. A `queue create` command would split settings across config and state. |
| D2 | Order within a queue: pinned, then priority, then position; `move` adopts the neighbor's priority and pin; `priority`, `pin` and `unpin` keep the job's position key, so it lands by age within its new band ([Order within a queue](interface.md#order-within-a-queue)). (pass 2) | Submitters can express classes of work at `add` time (priority), humans reorder exactly (move). Adopting the neighbor's priority makes a move land where it was put. |
| D3 | Across queues: queue priority, then the oldest waiting head job; per-queue caps bound each queue ([Selection](interface.md#selection)). | Round-robin ignores that some work (responses on the user's own PRs) is more urgent; one global order would compare job priorities set independently by different tools. |
| D4 | `starting` counts as running; a queue's `free` counts every queued job (including those waiting for `not_before`); the global count includes, per queue, only the ready queued jobs that could start under that queue's cap; `effective_free` ≤ `free`; `cap: null` is unbounded; `capacity` always exits 0 ([Capacity](interface.md#capacity)). (pass 1) | A slot must be held while `pre-start` hooks run, or a slow gate lets more jobs start than the cap. Counting a queue's whole backlog globally let one queue with a deep backlog report no global room for every other queue, although those jobs cannot start anyway (maintainer decision, review pass 1). Free capacity is data, not an error. |
| D5 | The pass only claims and spawns; the shim runs `pre-start` hooks while holding the slot ([Pass](interface.md#pass), [Start sequence](interface.md#start-sequence)). | Gate hooks can take up to 600 s; running them in the pass would stall every queue. Claiming before the hooks prevents over-claiming. |
| D6 | Early start triggers (list in D36) with `auto_run` to disable them ([Start triggers](interface.md#start-triggers)). | Jobs start within about a second without cron; cron remains the safety net. Concurrent passes are safe (runner lease, `BEGIN IMMEDIATE` claims) and coalesce (D28). |
| D7 | Every jobsctl process builds one [canonical environment](interface.md#canonical-environment) at its start, in the order that section defines; a configured `env.set.PATH` replaces the inherited `PATH` there, `env.path_prepend` applies after it, and setting it is recommended. The canonical environment never holds `env_file` values: they are added only to hook environments (minus the ignored names that section lists, which include `PATH`; `--pass-env` may still pass an ignored name to a job) and, through `--pass-env`, to jobs; internal processes are spawned with the canonical environment and read the file themselves when they need it ([Internal processes](interface.md#internal-processes)). A job gets the canonical environment restricted to `env.inherit`, then `env.set`, `env.path_prepend`, `--env`, `--pass-env` ([Job environment](interface.md#job-environment)). `--pass-env` values come only from `env_file`: an undefined name is a warning at `add` (`pass_env_undefined`) and a `missing_env` failure at start; jobs that need it are skipped, keeping their place, only while a configured `env_file` is unavailable (with `env_file: null` they are claimed and fail `missing_env`). `env_file` is a trust anchor (the file and ancestor checks of [Canonical environment](interface.md#canonical-environment), else `env_file_unsafe`) and holds secrets only: every value is masked and refused in argv and `--env` (D18); non-secret fixed values go in `env.set`. Hooks get the canonical environment minus `hooks_strip_env`. There are no `JOBSCTL_<KEY>` config variables; `--config` is made absolute and passed to every internal process (triggered passes, `_shim`, `_deliver`, `_kill`); config is per invocation while the state dir is shared. (pass 1, pass 2, pass 3, spot checks) | A pass can be started by cron, an interactive shell, someone's `cancel` or a finishing shim, so "the runner's environment" (architecture v1.10), and the first design's "allowlist from the starting process", made a job's environment, its secrets and even its caps depend on an arbitrary trigger chain (review pass 1; e.g. an empty `JOBSCTL_GLOBAL_CAP` in one `add` unbounded every queue). Config only from files and secrets only from the user's file make caps and secrets independent of the trigger; a submitter cannot inject values and nothing secret is stored (maintainer decision, review pass 1). Inherited values, `PATH` above all, still come from the process that started the chain (a shell's temporary `PATH` entry outlived the shell in later passes), so only `env_file`, `env.set` and `env.path_prepend` are trigger-independent: `PATH` is cleaned, and a fixed `PATH` is set with `env.set.PATH` plus `path_prepend` (review pass 2). An `env_file` line for `HOME` or an XDG variable sent every later jobsctl process to another config and state dir, and `LD_PRELOAD` or `PYTHONPATH` ran code inside it; the file's values reach running code as the user, so it is guarded like code (safety check). Restating the order here had drifted from the interface, "minus the `env_file` values" left open whether a variable the file overrode was removed or restored, and one rule for every `env_file` value (a secret) is simpler than telling secrets from fixed values in the same file (review pass 3). `env.set.PATH` applied only to jobs, so an agent-writable `PATH` entry from the trigger chain (a worktree's `node_modules/.bin`) still reached unsandboxed hooks holding every `env_file` value; and since every `env_file` value is a secret, none of them has a reason to steer jobsctl's own processes or a hook's shell (`PATH`, `SHELLOPTS`) (SAF2-2, SAF2-7). Architecture change (v1.11). |
| D8 | cwd defaults to the caller's cwd at `add`; `argv[0]` is resolved at start against the job's `PATH` and the result recorded (it must be absolute, else `spawn_failed`; kept when resolution succeeded and exec failed); no existence checks at `add` ([`add`](interface.md#add), [Start sequence](interface.md#start-sequence)). Passes, shims and the internal processes (`_deliver`, `_kill`) run with the state dir as their cwd; only the job process gets the job's cwd. (pass 1, pass 2) | The command may exist only in the job's environment (cron's `PATH` differs from the submitter's); resolving at start with the recorded result is deterministic and debuggable. A jobsctl process sitting in a job's cwd would keep a removed worktree's directory busy and make relative paths depend on the trigger. |
| D9 | No timeout by default; per job (`add --timeout`, `none` overrides a queue timeout) or per queue; the clock starts at `running`; expiry runs the signal sequence. `kill_grace` is per queue (`queues.<name>.kill_grace`) and per job (`add --kill-grace`) ([Timeouts](interface.md#timeouts), [Signal sequence](interface.md#signal-sequence)). (pass 1) | Agent jobs legitimately run for hours or days. A configured timeout is an explicit opt-in, so its automatic kill does not conflict with the human-only `cancel --force`. An agent job's forwarding chain (agent-spawn → supervise → exec → claude) needs longer to finish its bookkeeping than a shell job; one global grace either cuts agents short or makes every cancel slow. |
| D10 | Each job runs in a process group the shim creates; termination escalates SIGTERM to the PID, then SIGTERM and SIGKILL to the group; leftovers after a natural exit are only counted. The shim waits with `waitid(WEXITED\|WNOWAIT)` and keeps the leader unreaped until the signal sequence and the leftover probe are done. Hook processes follow the same rule: the firing process is the hook's parent (for an async hook, `_deliver`, D39), keeps the leader unreaped until every group signal and probe are done and never signals a group after reaping its leader; a hook timeout sends SIGTERM to the group, then SIGKILL after 5 s. On Linux every exact-PID signal (shim, job, hook leader; nothing signals `_kill`) uses `pidfd_open`, an identity check and `pidfd_send_signal`; the group signal of a `shim_lost` force cancel (D38), whose leader is no jobsctl process's child, uses `PIDFD_SIGNAL_PROCESS_GROUP` on Linux 6.9 and later and otherwise accepts the remaining window. Where pidfds are unavailable (macOS, an architecture outside the system-call fallback's allow list, `ENOSYS`, seccomp `EPERM`, WSL1) the identity is re-checked immediately before `kill`/`killpg` ([Exact signals](interface.md#signal-sequence); implementation notes). Processes other than the job's own PID that left the group are never signaled ([Signal sequence](interface.md#signal-sequence), [Leftovers](interface.md#leftovers), [Hooks](interface.md#hooks), [Residual risks](interface.md#residual-risks)). (pass 1, pass 2, pass 3, spot checks) | Spike A4: SIGTERM to a shell job's exact PID leaves its children running under PID 1. Signaling the exact PID first keeps the architecture's forwarding chain in charge; the group steps clean up shell jobs. A zombie leader keeps the process group id reserved and verifiable on every platform (macOS has no subreaper); a pidfd closes the gap between the identity check and the signal. A reaped hook leader (after a pipe EOF, or a double-forked async hook) freed its PID, so a later timeout or cancel could `killpg` an unrelated process group that reused the number (safety check). The windows that remain (older kernels, macOS, Linux without pidfds) are listed as residual risks; a fallback that hard-coded the system-call numbers would call a different system call on some architectures (SAF2-4). Requires extending the architecture's process-group exception from hooks to jobs a tool runs (v1.11). |
| D11 | A dead shim with a live job keeps the job `running` (`shim_lost`), holding its slot; jobsctl never kills it automatically and no longer enforces its timeout. When the shim and the job are gone, reconcile finalizes the attempt from the shim's result file if there is one (D30), ends a job with a committed `force_requested_by` `canceled` (`forced`), and otherwise marks it `failed` (`lost`). After a reboot, a `starting` attempt whose shim never confirmed is requeued (`boot_changed`, action `requeued`, attempt deleted); only confirmed shims and `running` jobs end `failed` (`lost`). `cancel --force` applies these rules to its target first; for a `shim_lost` job whose process still lives it hands the signal sequence to `_kill` (D38). An exit record of kind `unknown` means no exit status was observed (lost, or forced after a shim loss); its `leftovers` is counted when the process group is still verifiable, else `null` ([Liveness and recovery](interface.md#liveness-and-recovery), [Reconcile](interface.md#reconcile), [Exit record](interface.md#exit-record)). (pass 1, pass 2, pass 3) | Spike A5: the job keeps running after its shim dies; marking it failed would free a slot that is still in use and could start a second agent next to a live one. Enforcing a timeout without the shim would be an automatic kill of an unsupervised process. A forced cancel whose shim died before recording the end is still the human's cancel. A claim made just before a reboot ran nothing, so failing it reported a failure for work that never began, while the same claim without a reboot was requeued (review pass 3). |
| D12 | Holds carry a reason (`manual`, `escalated`, `exit_13`) that decides how they end: `release` requeues `manual` and (with a human `--override-escalation`) `escalated` holds and clears `not_before`; `retry` requeues `exit_13` holds (D14); `resolve` ends any held job for good. `release --override-escalation` and `cancel --force` are human-only. An `escalated` hold ends its attempt; `release` requeues the job and the next claim creates a new attempt. `release` of a queued job is a no-op; `not_escalated` applies only to `manual` and `exit_13` holds. `override_hooks` is kept until a start has actually run the `pre-start` hooks, also across `starting → queued` returns and automatic retries of starts that ran none; only `retry` and a terminal end clear it otherwise ([Hold reasons](interface.md#hold-reasons), [`hold` / `release`](interface.md#hold--release), [Human-only flags](interface.md#human-only-flags)). (pass 1, pass 2, pass 3) | Matches architecture §5.1/§12.4 (only pre-start escalations are released; exit-13 holds belong to their submitter, who resolves or retries them) and claude-session's `--override-escalation` gate. One attempt per claim keeps attempts comparable and makes the override apply to exactly one start. A start that failed before its hooks (a config error, a SIGTERM) and was retried automatically used to lose the human's audited override, so the next start escalated again; `retry` is a new decision and starts without it (review pass 3). |
| D13 | `resolve --as done\|failed\|canceled` (default `done`) ([`resolve`](interface.md#resolve)). | Submitters resolve after the work continued elsewhere and usually finished; the explicit status keeps statistics honest. |
| D14 | `retry` requeues a terminal job, or a job held `exit_13`, under the same id; the next claim creates a new attempt. For an `exit_13` hold, one transaction keeps the held attempt as recorded (status `held`) and requeues the job; no terminal hook fires and the action is audited as `retry`. `retry` of `manual` or `escalated` holds exits 20 (`not_terminal`; use `release`). `retry` records `retried_from_attempt`; with `--attempt N` it is a no-op (`changed: false`) whenever `attempt` is above N, or `retried_from_attempt` and `attempt` are both N, whatever the status, and N above `attempt` exits 20 (`attempt_mismatch`). `retry --timeout`, `--max-retries` and `--kill-grace` replace the corresponding `overrides` (audited in `inputs`). Automatic retry is opt-in per queue for the reasons `exit`, `signaled`, `terminated`, `lost`, `timeout`, `spawn_failed` and `missing_env`: the failed attempt is recorded and the job returns at once to `queued` with `not_before = now + retry_delay`, keeping its unique key; the 3rd consecutive shim-spawn failure is final. The decision uses the attempt's recorded `effective.max_retries` when one exists (shim, `_kill` and reconcile alike), else the current config. Every requeue puts the job at the bottom of its priority band with `enqueued_at` reset. `post-fail` fires for every failed attempt (a pending retry shows as `job.status` `queued`); the budget counts automatic retries since the last `retry` or `release` ([`retry`](interface.md#retry), [Automatic retry](interface.md#automatic-retry), [Hold reasons](interface.md#hold-reasons)). (pass 1, pass 2, pass 3) | Keeping the id keeps `JOBSCTL_JOB_ID` and the `job=` label that resume-aware job commands use to find their agent (architecture §5.1). A job parked as `failed` until its retry was due looked final to `wait`, notifications and `--unique-key` (a duplicate could be added) and needed its own reconcile step; queued with `not_before`, `cancel`, `hold` and `wait` just work (maintainer decision, review pass 1). Requeuing at the bottom of the band keeps a failing job from holding its queue's head (pass 1 said "keeping its place"; aligned with the interface in pass 2). Retrying an exit-13 hold lets a submitter rerun a job under its id once the cause is fixed, without first resolving it, which fired a terminal hook (maintainer decision, review pass 2). A status-based no-op rule let a replayed `retry --attempt N` undo a human's cancel of the requeued job or refuse after a hold; without overrides on `retry`, a job that timed out under `add --timeout` could only rerun with the same limit or be re-added under a new id, breaking resume-aware job commands; and the shim and reconcile decided retries from different `max_retries` values when config changed during a run (review pass 3). |
| D15 | `cancel` of `starting` jobs needs no `--force` (D27); selectors with `--all`; a new `post-cancel` hook. `cancel` with selectors prints `cancel.json` on exit 20 (nothing canceled, something refused); every other non-zero exit prints `error.json` ([`cancel`](interface.md#cancel), [Errors](interface.md#errors), [Hooks](interface.md#hooks)). (pass 3) | Nothing runs yet while `pre-start` hooks run. Workflows cancel queued work by unique key. Canceled jobs should not look like failures to notification rules. An exception covering every non-zero exit dropped the details of `cancel_pending` and `ambiguous` (review pass 3). |
| D16 | Unique keys are global across queues and enforced by a partial unique index; a collision returns the existing job ([Unique keys](interface.md#unique-keys)). | A key names a piece of work, not a queue slot; the index makes racing `add`s safe. |
| D17 | Output: one combined pipe read by the shim into a ring buffer, a 16 KiB / 200-line masked and sanitized tail per attempt, flushed every 5 s while running, no full log file. Live flushes withhold everything after the last newline and at least the longest masked value's length minus one trailing bytes; only the final tail includes a trailing partial line. A window without any newline first discards its first (longest masked value + 256) bytes ([Output capture](interface.md#output-capture), [Masking and sanitizing](interface.md#masking-and-sanitizing)). (pass 1, pass 2) | Spike B4: file capture cannot be capped safely; pipes cost little memory; one stream keeps stdout/stderr order. Spike B6: 16 KiB per job is about 160 MiB for 10,000 jobs (47 MiB compressed), hence compression and retention. A live flush cut at the window's end could show the start of a secret still being written. In a newline-free stream the line-boundary cut has nowhere to land, so the window's start could hold the tail of a secret cut off before it (safety check). |
| D18 | Masking keeps extra raw context and cuts after masking on a line boundary; it covers `mask_env`, every `--pass-env` variable and every variable defined in `env_file`, taking the union of the canonical-environment read and the job-start read of `env_file`; values under 8 characters are not masked (warned at start); tails are sanitized at store and at display. `add` refuses (exit 2) an argv element or `--env` value that contains a masking-set value of 8 or more characters (`secret_in_argv` with the argument index, `secret_in_env` with the name) and `--env NAME` for a name defined in `env_file` or listed in `mask_env`; `unique_key_reused` logs `argv_sha256`, never argv. Masking is best-effort: only those variables' values are masked, never secrets a job obtains itself ([Masking and sanitizing](interface.md#masking-and-sanitizing), [`add`](interface.md#add), [Residual risks](interface.md#residual-risks)). (pass 1, pass 2) | Spike B5: masking after a naive cut leaked partial secrets in 187 of 200 streams; very short values mask ordinary text. Spike B7: tails can carry terminal escape and bidi injection. `env_file` holds the user's secrets by design (D7), and its values can reach a job through `env.inherit`. The file can change between the two reads, so masking with one read could miss the value the job got. A token passed as `--env GITHUB_TOKEN=…` or in argv was stored in `state.db` and printed by `show --json` (review pass 2, safety check). |
| D19 | No `repos:` map and no derived repo; the queue is the scoping unit and per-queue settings take the place of per-repo overrides in the precedence order ([Queues](interface.md#queues), [Config](interface.md#config)). | A job is an argv; one queue holds jobs for many repos. The design guide's per-repo rule assumes a repo notion jobsctl does not have (design guide exemption, v1.11). |
| D20 | `wait` with outcome exit codes 0/12/13/20 and its own timeout 22; a pending automatic retry keeps it waiting. `add --wait` prints `add.json` with the `show`-shaped job and, after a successful add, exits with `wait`'s codes; Ctrl-C only stops waiting: it prints the current job (as for exit 22) and exits 130 ([`wait`](interface.md#wait), [`add`](interface.md#add)). (pass 1, pass 2) | Lets humans and scripts block on a job without a polling loop. Reuses reserved codes; 22 is the only tool-specific code. One output shape keeps `created` and `queue_created` visible to waiting callers. |
| D21 | Audit only actions that override a safety default or end someone's work; `--actor`/`--decision-id` on every mutating command; jobsctl's own transitions and retention prunes use the reserved actor `auto:jobsctl`, which the CLI refuses (exit 2). `--decision-id` on a command that writes no audit record goes into its log record (`transition`, `reorder`, `label`). Audit actors are claims, not proof ([Audit and log](interface.md#audit-and-log)). (pass 1, pass 2) | jobsctl posts nothing externally; the log already records every transition. A fixed actor separates automatic from requested changes, which only holds if callers cannot claim it. Decision ids were silently dropped by non-audited commands (review pass 2). |
| D22 | Hooks: architecture's five plus `post-cancel`; payload `repo: null`; at-least-once in-order delivery through an outbox for post hooks; no `pre-add` in v1. `pre-start` is not an outbox event: the shim runs it, and its payload `event_id` is `<claim_id>:pre-start:<hook index>`. A hook entry opts into the output tail with `include_output` (default `false`); every payload carries `output_available`. Hook entries may be named (the hook identity in `vetoed_by` and `override_hooks`). Hook stdout and stderr are read in memory (stdout parsed for `decision_id`) and not stored: `log.jsonl` gets a `hook_ran` event and, only on failure, timeout, veto or escalation, at most 2 KiB of masked, sanitized stderr; a veto's or escalation's message goes to the attempt's `hook_messages` ([Hooks](interface.md#hooks), [Hook processes](interface.md#hook-processes), [Payload](interface.md#payload), [Delivery](interface.md#delivery)). (pass 1, pass 2, pass 3) | Same delivery guarantee as claude-session; `pre-add` has no clean escalation shape and submitters have their own pre-enqueue hooks (hook feature candidate in the roadmap). Tails are untrusted and can hold secrets masking missed; hooks that only notify should not receive them unless configured to (maintainer decision, review pass 1). The log is long-lived and read by other tools, so it should not be the largest copy of untrusted, possibly secret-bearing hook output; the human deciding `--override-escalation` needs the escalation's reason on the attempt, not in the log (safety check, review pass 2). A per-attempt store of hook output (pass 2) had no reader, cost up to 128 KiB per hook run and was a third copy of that output (SIMP3-1, review pass 3). |
| D23 | Process identity is `(boot_id, pid, start ticks)`; macOS through `libproc` (boot id: D32); never wall time or `ps` parsing ([Process identity](interface.md#process-identity)). | Spike A3: field 22 parsed after the last `)` is stable; `btime`-based epochs move with clock changes; `ps -o lstart` has 1-second resolution and macOS PIDs wrap at 99999. |
| D24 | `browse` (Textual) is an optional `tui` extra and the last plan stage; its keys follow design guide §10 (`r` refreshes; no deviation) ([TUI](interface.md#tui)). (pass 1) | The v1 bar (cap enforced, reorder works) needs only the CLI and the dashboard's `move`; consumers that only call the CLI should not pull in Textual. |
| D25 | `cron install` writes one `run --quiet` entry with the absolute `jobsctl` path, an explicit `PATH` (non-existent and temporary entries dropped with a warning) and `XDG_CONFIG_HOME`/`XDG_STATE_HOME` when set at install, and no env-file prefix; no `reconcile` entry. Every value written is single-quoted (with `'` escaped) and `%` is escaped; `PATH` entries with control characters are dropped and such XDG values left out (`path_entry_dropped` naming the variable, never the value). awkit's bundled jobsctl adapter declares the same line (architecture §7.7) ([`cron install`](interface.md#cron-install--cron-uninstall)). (pass 1, pass 2, pass 3) | Spike A2: cron's `python3` was 3.10 and its environment minimal. Every pass reconciles. An unquoted space, `%` or newline changes what cron runs; both installers write the same tagged block, so a differing adapter line would drop the XDG values after `awkit cron install` and point cron's pass at another state dir (review pass 2). **Deviation from design guide §4.3** (optional user-owned env-file prefix): every pass loads `env_file` itself (D7), so a cron-level prefix would only add a second source that can disagree with it; the XDG variables make cron's pass use the same config and state as the user's shell (maintainer decision, review pass 1). |
| D26 | A job ended by a SIGTERM that did not come from `cancel --force` (no committed `force_requested_by`), e.g. shutdown or logout, runs the signal sequence and ends `failed` with reason `terminated`: retry-eligible, `post-fail`, actor `auto:jobsctl`. A SIGTERM to the shim while the job is `starting` kills the running hook's process group and ends the job the same way, with exit `null` (a force request cannot exist there: `--force` on a `starting` job is a plain cancel). After the job exited, a SIGTERM makes the shim skip its remaining hook deliveries, which stay in the outbox for `_deliver`. A shim that gets SIGTERM while it waits for the job lease or delivers earlier events exits without writing; reconcile ends the job `failed` (`shim_dead`, `lost`, retry-eligible) or, before confirmation, requeues it (`claim_orphaned`) ([End reasons](interface.md#end-reasons), [Signal sequence](interface.md#signal-sequence), [Reconcile](interface.md#reconcile)). (pass 2, pass 3) | Recording every SIGTERM as `forced` claimed a human cancel that never happened and suppressed retries and failure notifications (maintainer decision, review pass 1). `forced` now holds exactly when `force_requested_by` is set. A shutdown can reach a shim at any point, so `starting` and the post-exit phase need defined outcomes too (review pass 2); before the lease, a shim may not write, so the phase before `pre-start` falls to reconcile (review pass 3). |
| D27 | Start atomicity: the claim records the claiming pass's identity (`claimed_by`) and a random `claim_id`, passed to `_shim` as an argument; every shim write is a compare-and-set on `claim_id`. The pass records the shim's identity on the attempt right after spawning it, in a follow-up transaction; the shim's first act only confirms that identity is its own; while the attempt has its `claim_id` but no recorded identity, it polls every 100 ms as long as the claiming pass is alive, and exits only if another identity is recorded, the `claim_id` differs or the claimer died without recording one. The shim then waits, without a deadline, for the `job:<id>` lease, holds it for its whole life, delivers its job's undelivered hook events in order and only then runs `pre-start`. `claim_orphaned` means a claim with no recorded shim identity whose claiming pass is dead, or a pass's own shim child that exited without confirming; `shim_dead` requires a recorded identity; a shim waiting for the lease is alive. `cancel` of a `starting` job is a compare-and-set to `canceled`. The shim re-reads its job after confirming, after taking the lease and before each `pre-start` hook, and polls it at least every second while a hook runs; once the job is no longer `starting` with its `claim_id`, it kills a running hook's group, runs no further hooks, delivers its job's undelivered events (including `post-cancel`) and exits. A pass returns a job whose shim could not be spawned to `queued` by a compare-and-set on `starting` with its `claim_id`, so a job canceled meanwhile keeps its attempt. The job is spawned inside one `BEGIN IMMEDIATE` that re-checks `starting`, spawns (fork/exec only), records the identity and sets `running`: the only process spawn inside a transaction ([Start sequence](interface.md#start-sequence), [Reconcile](interface.md#reconcile), [Leases](interface.md#leases), [`cancel`](interface.md#cancel)). (pass 2, pass 3) | Without these, a `cancel` could commit between the hooks and the spawn and a job would start after being canceled, and a reconcile could mark a freshly claimed job `lost` before its shim recorded itself (review pass 1). A fork/exec takes milliseconds, so holding the write lock for it is cheap; a cancel that loses the race sees `running` and gets `live`. A shim recording its own identity left a window in which reconcile requeued a healthy claim as orphaned, and the old shim could then adopt the new claim; recording at spawn and the `claim_id` close both. The lease holder is alive by definition and releases when its delivery ends, so the wait needs no deadline, and delivering earlier events first keeps hook order across attempts (review pass 2). A shim that reached its check before the pass's follow-up transaction committed found no identity and exited, so contention alone could fail healthy claims; a job canceled while its shim waited for the lease still ran its `pre-start` gate (review pass 3). |

(pass 2) | A trigger that found the lease held used to exit with nothing done, so a job added just after the holder's claim waited for cron. The counter keeps one pass running and none missed. ### Data model

`state.db` (SQLite, WAL, `synchronous=NORMAL`, `busy_timeout`, `journal_size_limit` 64 MiB; schema version in `PRAGMA user_version`; forward-only, additive-only migrations run by CLI commands at open under `BEGIN IMMEDIATE`, never by internal processes (D31)). Timestamps are UTC with millisecond precision. The public shapes are the [Job object](interface.md#job-object) and the [Attempt object](interface.md#attempt-object); the tables hold:

- `jobs`: `id`, `queue`, `argv` (JSON), `cwd`, `env` (JSON of `--env`), `pass_env` (JSON names), `unique_key`, `priority`, `pinned`, `position` (sortable text key), `status`, `reason`, `hold_reason`, `shim_lost`, `attempt` (number of the last kept attempt, 0 if none; decremented when a requeue deletes the attempt), `overrides` (JSON: `timeout` in seconds or `"none"`, `max_retries`, `kill_grace`; absent key = queue setting, D40), `not_before`, `auto_retries` (automatic retries since the last `retry` or `release`), `spawn_failures` (consecutive; reset on a confirmed shim, `retry` and `release`; `claim_orphaned` does not count), `override_hooks` (JSON), `retried_from_attempt`, `created_at`, `enqueued_at`, `status_changed_at`, `ended_at`, `resolved_by`, `note`, `actor`, `decision_ids` (JSON). `blocked_by` and the `effective` values of jobs that are not `starting` or `running` are computed, not stored. Partial unique index on `unique_key` where status is non-terminal; index on `(queue, status, pinned, priority, position)`.
- `job_labels`: `(job_id, key, value)`, primary key on all three.
- `attempts`: `(job_id, n)`, `claim_id`, `status`, `reason`, `hold_reason`, `claimed_at`, `claimed_by` (the claiming pass's identity), `shim_identity` (recorded by the pass), `shim_confirmed_at`, `effective` (JSON snapshot recorded by the shim at start, D40), `running_at`, `ended_at`, `exit` (JSON), `leftovers`, `job_identity`, `pgid`, `resolved_path`, `escalated_hooks` (JSON), `vetoed_by`, `hook_messages` (JSON: `hook_id`, `outcome`, `message`), `decision_ids` (JSON), `force_requested_by`, `resolved_by`, `note`, `jobsctl_version`. Created at claim; deleted if its shim cannot be spawned or the claim is orphaned (also by `boot_changed` for an unconfirmed shim), except that the attempt of the third consecutive spawn failure is kept (exit and `resolved_path` `null`). Hook output is not stored (D22).
- `outputs`: `(job_id, n)`, `tail` (BLOB; zlib above 4 KiB), `compressed`, `bytes_seen`, `truncated`, `updated_at`. A separate table keeps `list` fast (spike B6).
- `hook_outbox`: `event_id`, `job_id`, `seq`, `hook`, `payload` (JSON, including the labels at transition time), `async` (the hook entry is async, D39), `created_at`, `delivered_at` (for an async hook, when its hook process ended). Post hooks only; `pre-start` runs in the shim (D22).
- `leases`: `name` (`runner`, `deliver`, `job:<id>`), `holder_identity`, `expires_at`.
- `counters`: `name`, `value` (`pass_requested`, D28; one `seq` counter per log file, D42).
- `queues_seen`: `name`, `first_seen`; a row is deleted at retention when its queue is not configured and has no jobs left.
- `pruned_ids`: `id`, so ids are never reused after prune (one row per pruned id).

Outside the database, `shims/` holds each shim's diagnostics log (`<id>.log`) and its result file (`<id>.<attempt>.result`, 0600, D30), both removed with their job; `diag/` holds the diagnostics files of triggered passes and internal processes (`<kind>-<pid>.log`, 0600, deleted by every pass after 7 days regardless of `retention`, D43). Every diagnostics file is created on its first write and capped at 1 MiB. Retention and `prune` measure a job's age from `ended_at`.

Every connection uses `autocommit=True` and explicit `BEGIN IMMEDIATE` … `COMMIT` for writes (spike B1: a plain `BEGIN` that upgrades to a write fails with "database is locked" despite the busy timeout; Python 3.12's legacy transaction mode silently ignores `PRAGMA journal_mode=WAL` inside a transaction).

### Concurrency

- Claims count and claim inside one `BEGIN IMMEDIATE` transaction (spike B1: no cap exceeded under 20 concurrent passes); the claim records `claimed_by` and a fresh `claim_id`. The pass records the shim's identity in a follow-up transaction right after `Popen`, and the shim polls until it is recorded; every later shim write is a compare-and-set on `claim_id` (D27).
- Transitions are compare-and-set on `(id, status, attempt)`; `cancel --force` first commits `force_requested_by` on the attempt, then signals (or spawns `_kill`, D38); the final transaction reads it (D26).
- The `runner` lease makes concurrent passes cheap; the `pass_requested` counter makes the holder re-claim instead of losing a trigger. A trigger's increment and lease check share one transaction, as do the holder's final comparison and release; `reconcile` takes the `runner` lease too and re-checks the counter at release (D28).
- The `job:<id>` lease serializes everything that delivers a job's hook events or signals its processes: the shim (for its whole life, after waiting for the lease without a deadline), `_kill`, `_deliver` (per job), and the commands that deliver synchronously (`hold`, `cancel`, `resolve`), which hold it only while delivering. A new holder first delivers the job's earlier undelivered events, in order. Lease timings: D33 ([Leases](interface.md#leases)).
- The `deliver` lease allows one `_deliver` at a time; a pass spawns one only when no live holder exists, with the runner's counter re-check (D29).
- Async hooks: a lease holder leaves async events in the outbox and requests a `_deliver` spawn; `_deliver` runs them as their parent, at most 8 at once and one per job, outside the `job:<id>` lease, and marks each delivered when its hook process ended (D39).
- Every process reaps only the PIDs it spawned and recorded, never "any child" (D48); long-lived processes (`run --loop`, a waiting `cancel`) reap their exited children by PID each iteration; a pass that sees its own shim child exit unconfirmed marks that attempt `claim_orphaned` (D27).
- `run --loop`, a waiting `cancel` or `wait`, and `browse` check `user_version` before each iteration or transaction and exit on a newer one (`run --loop` re-execs itself, also on a changed installed version, D31).
- `seq` allocation takes an exclusive `flock` on the log file, then a short counter transaction, then appends (D42); no transaction is open while the lock waits, and no process logs inside a database write transaction (it logs after the commit).
- Long work (hooks, waiting on a job, delivery) never happens inside a transaction. The one process spawn inside a transaction is the job's fork/exec (D27).
- Retention deletes at most 100 jobs per transaction within the fixed 10 s per-pass budget and skips jobs with undelivered hook events (D29).

### Gateway boundary

`gateway.py` wraps process creation (`Popen` with `start_new_session`/`process_group`), `os.kill`/`os.killpg`, `pidfd_open`/`pidfd_send_signal` (including `PIDFD_SIGNAL_PROCESS_GROUP`), `prctl` (subreaper, dumpability), `waitid`/`waitpid`, `flock` and the clocks; `procs.py` reads identities through it. Unit tests replace both with fakes. Integration tests run real processes with a temporary `XDG_STATE_HOME`.

### Error handling

- Invalid config fails fast naming the key (never an `env.*` value); unknown queue selectors in hooks are always warnings (`strict_queues` affects `add` only). A shim reads config once at start; if it cannot, the job ends `failed` (`spawn_failed`, log `config_invalid`). Repeating warnings (`unknown_queue_selector`, `config_invalid` from passes, `path_entry_dropped`, `env_file_unsafe`) are logged once per change of state.
- Database busy beyond `busy_timeout` exits 1 (`busy`); a pass changes nothing and the next pass retries; a triggered pass that was busy before taking the lease re-spawns itself once after 2 s (D28).
- An internal process that finds a schema older than it knows exits before writing; a shim does so before confirming (not counted as a spawn failure), and the job is requeued (`claim_orphaned`) once a CLI command has migrated (D31). A non-additive change needs a new major version and its drain step.
- A shim that cannot be spawned leaves the job queued in its place (attempt row deleted); after 3 consecutive failures the job ends `failed` (`spawn_failed`) for good (not retried automatically), that last attempt is kept, and `run --json` lists it in `warnings`. The return to `queued` is a compare-and-set on `starting` with the `claim_id` (D27).
- The shim writes its result file, then retries the final commit with backoff for up to 10 minutes; if it gives up or dies, reconcile finalizes from the file (D30). A failed write of the final tail (disk full) still commits the final transition without a tail and logs a warning.
- A configured but unavailable `env_file` holds back the jobs that need `--pass-env` (`blocked_by: env_file_unavailable`); `env_file_unsafe` is logged once per change of state and `run --json` reports a warning (D7). Bad `env_file` lines are skipped with `env_file_line_invalid` or `env_file_line_ignored`, naming the line number only.
- Hook failures after the fact (post hooks) are logged as `hook_ran` with at most 2 KiB of masked, sanitized stderr, never fatal (D22).
- The shim's and the internal processes' own exceptions go to their diagnostics files, never with environment values (D43); the job is finalized by the next reconcile (or by `_kill`, re-spawned by reconcile, D38).

## Implementation notes

Plan-level choices that do not change the interface (review pass 3):

- `pruned_ids` grows by one row per pruned id; that is acceptable.
- `procs.py` uses `os.pidfd_open` and `signal.pidfd_send_signal` when the interpreter has them; otherwise it calls `pidfd_open` (434) and `pidfd_send_signal` (424) through `ctypes` `syscall()` with `c_long` arguments, because uv-managed CPython builds compile them out (spike C1). That fallback is used only on allow-listed Linux architectures where those numbers hold (x86_64, i386, aarch64, arm, riscv64, ppc64le, s390x; not x32), and the identity check runs after `pidfd_open`, on the pidfd's process. On other architectures, and on `ENOSYS` or `EPERM`, the identity is re-checked immediately before `kill`/`killpg` ([Exact signals](interface.md#signal-sequence); spot checks, SAF2-4).
- Group signals use `os.killpg` on every kernel, safe because the leader is held unreaped ([Signal sequence](interface.md#signal-sequence)); `PIDFD_SIGNAL_PROCESS_GROUP` is used only for a `shim_lost` force cancel on Linux 6.9 or later (D10, spike C1).
- After reaping a leader held with `WNOWAIT` through `os.waitpid`, the code sets `Popen.returncode` itself, so a later `wait()` or `poll()` does not fail with `ECHILD` (spike C2).
- When probing a group for live members, a non-leader member in state Z counts as dead, so a zombie whose parent is outside the group cannot keep a wait loop spinning (spike C3).
- Hook selectors (`queues`, `exclude_queues`, `labels`) are evaluated against the job's labels at transition time; the event stores them, so a later label change does not change who receives it.
- A duplicate hook `name` within one hook list is `config_invalid`.
- `run --max-starts N` counts claims across the pass's repeated claim loop.
- `export --since` and `--after-seq` combine with AND; `--since` accepts RFC 3339 timestamps with any offset.
